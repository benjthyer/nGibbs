## YAML recommendations

Recommendations below are drawn entirely from the training-log loss curves and the training code's own logic (`trainer.py`, `sobolev.py`), since `ModelComparison.py` couldn't run against these `ContinuousModel` checkpoints (see Training-stage notes above). All target `recipes/training/HeFESTotuneyContinuous.yaml` — none applied, per instructions to ask first.

### 1. Cap dropout at 0 for `train1`/`train2` — the adaptive controller is actively hurting this architecture

**Root cause, precisely identified:** `sobolev.py`/`trainer.py`'s adaptive regularizer triggers "Overfitting → increase dropout" whenever `avg_test_loss > avg_train_loss * 1.02` — a **2% relative gap, checked every single epoch**, not a sustained trend. At `train2`'s loss scale (~27-33k) that's an easy bar to cross from ordinary batch-to-batch noise alone, so the trigger fires on what's often just noise, not real overfitting. Once triggered, it bumps dropout `0.0 → 0.02` against a ceiling of `0.3` (inherited from `tune2`/`tune4`'s `encoder_regularization`/`mole_regularization: '...dropout0.3'`). That small dropout bump then measurably degrades the *actual trained weights* for 2-3 epochs (both train **and** test loss get worse, since it's not just eval-time variance — see epoch 47→48 in train1: test 161.6→407.2; epoch 16→ in train2: test 26748-ish plateau spiking to 32202). In `train2` this recurred at least 5 times (epochs 8, 16, 19, 21, 26) and is the most likely reason the run never beat its epoch-13 best (26747.83) despite running 20 more epochs to early-stopping — two near-misses (epoch 25: 26749.68, epoch 28: 26927.38) suggest the model kept almost re-finding that optimum before a dropout bump knocked it away again.

**Recommendation:** in `train1:` and `train2:` blocks, override the inherited regularization strings to cap the ceiling at 0, e.g. add:
```yaml
train2:
  ...
  encoder_regularization: 0.05layernormdropout0.0   # ceiling 0.3 -> 0.0: adaptive dropout can no longer engage
  mole_regularization: 0.0layernormdropout0.0
```
(keeping the *initial* rate from the tuned baseline, only zeroing the ceiling). With `max_drop=0`, the "Overfitting" branch's dropout-increase condition (`min(dropout_rate + dropout_step_up, max_drop) > dropout_rate`) becomes false, so a spurious trigger falls through to the much gentler noise-increase branch (`noise_step_up=0.002`, additive on an input-noise term) instead of perturbing the network's actual layers. This is a pure YAML change, no code touched.

**If it's still worth reproducing the adaptive-dropout behavior for other runs**, the trigger threshold (`* 1.02`) and step sizes (`dropout_step_up=0.02` default) live in `trainer.py`/`sobolev.py`, not YAML — that would be a source change (hysteresis: require 2+ consecutive over-threshold epochs before acting, or loosen `1.02` to `~1.15`) worth considering separately, but is a design change I'd want to confirm with you before making, not something to fold into this batch of YAML edits.

### 2. `tune2`/`tune4` regularization sweeps are budget-starved and effectively uninformative

**Evidence:** in both `tune2` (`encoder_regularization` sweep, `epochs: 8`, `early_stopping_patience: 3`) and `tune4` (`mole_regularization` sweep, same budget), **every dropout value above the lowest tested one failed to beat its own fresh-init baseline within the 3-epoch window** — `tune2`: dropout ceilings 0.1 and 0.2 both "no epoch improved on it"; `tune4`: ceilings 0.05/0.1/0.2 all "no epoch improved on it" too. Each trial shows classic cold-start underfitting (huge epoch-1 loss, still falling fast at epoch 3 when the window closes) rather than a genuine comparison of regularization strength. The sweep is currently just selecting "whichever config happened to warm up fastest in 3 epochs," which is close to meaningless signal for choosing a regularization ceiling that then gets used for the entire multi-hour `train1`/`train2` run.

**Recommendation:** raise `tune2`/`tune4`'s `epochs` from 8 to ~15-20 and `early_stopping_patience` from 3 to ~5-6, giving each sweep trial enough runway to actually differentiate. This costs more tuning wall-clock time (each trial is currently only ~4s/epoch, so even doubling the budget is cheap relative to the `train1`/`train2` stages that follow) but produces a much more trustworthy regularization choice feeding into the long runs.

### 3. Per-phase/per-oxide loss weighting — unable to verify this cycle

`ModelComparison.py`'s per-phase precision/recall and per-oxide composition-error breakdown (which would normally inform `binweights`/`compweights` adjustments) isn't available for these `ContinuousModel` checkpoints — see the Training-stage note on `emulator.py`'s `MidLevelNetwork`-only assumption. No changes recommended here this cycle; worth revisiting once that comparison path is extended to support `ContinuousModel`, if that's a priority.

### Summary of concrete proposed edits
- `train1`/`train2`: zero out the dropout ceiling in `encoder_regularization`/`mole_regularization` (keep initial rate, change only the number after `dropout`).
- `tune2`/`tune4`: raise `epochs` (8→~15-20) and `early_stopping_patience` (3→~5-6) so the regularization sweep produces a meaningful signal.
- Separately, consider (as a source-level change, not YAML, and only with your go-ahead): loosen the `avg_test_loss > avg_train_loss * 1.02` overfitting trigger in `trainer.py`/`sobolev.py` to require a sustained gap rather than a single noisy epoch.
